# Data Quality and Validation

## 1. Quality Is a Release Gate

The number of records in a catalogue is not a quality metric by itself. The system should optimize for accurate discovery, traceability, and useful coverage. A large set with irrelevant records, broken links, merged identities, or undocumented provider failures can be less useful than a smaller, verified set.

## 2. Current Known Risks

- Historical generated category pages contain demonstrably irrelevant records in at least one category. The previous classifier could force an item into the category associated with its search query even when the returned document title was unrelated.
- The checked-in historical output has not been regenerated by the revised classifier in this branch.
- Provider coverage is not yet fully measured. A module being present in the code does not prove successful end-to-end collection.
- Some provider adapters currently report only normalized metadata, and not all request outcomes are represented as a complete run-state record.
- Provider-specific citation counts can differ; one integer without source and observation time is not a fully defined metric.
- Access labels remain a heuristic layer and should not be treated as a definitive legal or full-text availability assessment.
- The current rule-based classifier is not calibrated. Matched patterns explain decisions but do not represent statistical confidence.
- Sources and URLs in the curated registry are seed entries; automatic link-health monitoring is not yet implemented.

These limitations must be reflected in release notes and user-facing claims until measured and addressed.

## 3. Record Counts

Use separate metrics for distinct concepts:

- **Raw records:** total provider result records received before normalization and deduplication.
- **Unique records:** records remaining after identity resolution under a documented policy.
- **Category assignments:** all record-to-category edges. One document may contribute more than one assignment.
- **Unclassified records:** unique records for which no category met the rule requirements.
- **Provider query success:** queries completed with parseable responses according to the provider contract.
- **Provider query empty:** successful queries that returned no valid records.
- **Provider query failure:** queries that failed, exhausted retries, or returned an unusable response.

The category assignment total must not be presented as the number of unique documents. Source counts should reconcile to the unique-record population; category counts should reconcile to category assignments.

## 4. Deduplication Policy

The current safer baseline prefers DOI identity and otherwise uses complete normalized bibliographic identity with author and year or year and venue. It no longer truncates titles to a fixed prefix and does not automatically merge records that have distinct DOIs. Records without enough identity fields are retained rather than silently merged.

This policy is intentionally conservative. It may retain duplicates when identity data is incomplete, but that is preferable to irreversible false merges. Future fuzzy matching should produce candidate pairs and evidence for review, not automatically delete ambiguous records.

When duplicates do merge, missing fields may be filled from the additional record. Source provenance should remain inspectable. Source-specific values such as citation counts should eventually be stored as separate observations rather than blended into one unexplained field.

## 5. Classification Validation

The classifier must not assign a category solely because the search query came from that category. The source query bucket is provenance, not proof of relevance.

Before a release, create a manually reviewed benchmark covering all major taxonomy blocks, including:

- Relevant, irrelevant, and ambiguous titles.
- Acronyms with unrelated meanings.
- Titles with missing abstracts and metadata.
- Cross-disciplinary papers that mention finance incidentally.
- Documents that legitimately belong to multiple categories.
- Resource types beyond journal articles as those adapters are added.

Report precision, recall, F1, false positives, false negatives, unclassified coverage, and category-level confusion. Set release thresholds after measuring the benchmark; do not claim a target has been achieved from a handful of hand-picked examples.

## 6. Recommended Acceptance Gates

A high-quality release should satisfy all of the following:

1. Unit tests, compilation, and offline integration tests pass.
2. No credential literals remain in the current source or fixtures.
3. Historical credentials are rotated; removing values from the current revision is not treated as revocation.
4. Provider success, empty-result, failure, retry exhaustion, and pagination termination are reported separately.
5. Every exported record includes a stable identity where the provider offers one, or an explicit indication that identity is incomplete.
6. Classification assignments include explainable evidence and are evaluated on the reviewed benchmark.
7. Unique-record and category-assignment counts are separate and reproducible.
8. Representative output pages are manually reviewed after a fresh rebuild.
9. The curated registry validates structurally and is checked for link health before a release.
10. Generated artefacts can be rebuilt from documented inputs and a known code revision.

## 7. Reproducibility Manifest

For each generated dataset snapshot, record:

- Snapshot identifier and generation time in UTC.
- Repository commit and application version.
- Search taxonomy and classifier versions.
- Provider and endpoint names.
- Query count and exact query-list version.
- Queries attempted, succeeded, empty, failed, and rate-limited.
- Raw, unique, duplicate, categorized, and unclassified counts.
- Validation benchmark version and observed metrics.
- Access classification policy version.
- Export filenames and SHA-256 checksums.

A snapshot should be reproducible from stored inputs without depending on the current state of every external API.
